# Agent Guide

Use this guide for future Codex or agent work in this repository.

## Project Facts

- `runnerd` reads `./runnerd.yaml` by default, or another path passed with `--config`.
- Local development should use `runnerd.local.yaml` for secrets and sqlite state.
- Sensitive scalar config fields accept plaintext or `RUNNERD_ENC(v1:...)` generated by `runnerd --obfuscate-config-value`. The format only hides plaintext from casual inspection because its decoding key is embedded in runnerd. Keep sensitive values typed as `config.Secret`, call `Value()` only at their use sites, and preserve masked text, slog, JSON, and YAML output.
- UI source lives in `ui/`.
- Production UI assets are generated into `internal/server/ui/` by `task ui-build` and embedded by `internal/server/ui_assets_production.go`.
- Development UI assets are proxied to Vite by `internal/server/ui_assets_development.go`.
- `/` is always the public Qiniu CI Runner landing page. `/docs` and the exact guide routes declared in `ui/src/site-doc-routes.ts` are public; their paired English/Chinese Markdown sources live under `ui/src/content/site-docs/`. `/jobs` is the protected ordinary-user Jobs homepage. `/repositories` is the canonical GitHub repository access and effective Sandbox service readiness page; `/account/repositories` and `/organizations/{login}/repositories` are compatible scoped links to the same surface. `/runner-specs` is the protected, scope-free, read-only platform Runner Spec catalog. Account settings under `/account/runner-specs` and matching Organization routes manage only that scope's custom Specs; other protected settings include preferences, Sandbox templates, and Sandbox instances. Signed-out deep links must preserve their same-origin destination through OAuth `return_to`; unknown routes render 404.
- Ordinary-user Jobs authorization must use exact `(github_installation_id, repository_full_name)` pairs from the intersection of the stored GitHub user access token and each account-linked GitHub App installation. Never authorize Jobs from an installation link or installation-wide token alone; apply the same check to lists, details, groups, logs, and terminals, and fail closed when the user token is unavailable or rejected.
- Sandbox service credentials and provider resource catalogs are ordinary-user account or organization data. Keep credential editing in the account or organization Preferences surface; `/repositories` only shows effective readiness and links there when a manageable scope is missing configuration. Repository-only access can make an organization installation and its authorized repositories visible, but Settings lists only the signed-in account and organizations where the user has an active GitHub membership. The GitHub App therefore requires organization `Members: Read-only`; every existing installation owner must approve that permission when it is added, otherwise eligible organizations remain hidden from Settings. Apply the same manageable-scope check to installation-scoped Sandbox mutations and catalog reads; outside collaborators get read-only readiness status only. Keep credential-bound `/user/sandbox/templates` and `/user/sandbox/instances` separate from admin configuration APIs and from unauthenticated `GET /api/public/runner-templates`, which exposes only stable runnerd-owned public template names, logical Runner Spec names, and workflow labels.
- Current admin browser routes include `/admin/`, `/admin/accounts`, `/admin/runner_requests`, `/admin/runner_requests/{id}`, `/admin/sandbox_service`, and `/admin/diagnostics`; keep admin routes and role-gated APIs explicit when changing shared `ui/` code. Treat a Runner request as its own resource: the collection accepts exact Runner Name or internal Request ID lookup, resolves an exact Runner Name before an equal internal ID, and then navigates to the canonical internal-ID detail path. The canonical page aggregates persisted state, findings, the current GitHub Job result, and a cursor-paged mixed event timeline. Cache successful GitHub Job lookups briefly and coalesce concurrent lookups for the same Job so active-page polling cannot consume GitHub rate budget on every refresh. Diagnostic findings must use only a separately bounded `control_log` tail so raw output cannot create false signals or displace control evidence. The timeline loads newest events first, uses an exclusive `before_id` cursor for older pages, and renders every persisted control/stdout/stderr event directly as an individual chronological row without nested output cards or disclosures. Active request details refresh automatically through exclusive `after_id` pages until caught up, keep the older-history cursor independent, and merge new events without discarding or skipping loaded history; explicit refresh and stale-response protection remain required. Reserve Admin Diagnostics for current-process expvar, redacted runtime configuration, and pprof discovery. Keep diagnostic and event lookups admin-only, bounded, credential-free, useful when remote lookups fail, and keep legacy diagnostic deep links compatible.
- `/admin/accounts` lists OAuth/bootstrap-created accounts and linked identities. Its only mutation changes another account's `admin`/`user` role atomically with an audit event; self-role changes and changes that could leave no administrator are rejected.
- Runtime state can use sqlite, Postgres, or MySQL. Do not document multi-instance support until two runnerd processes have been verified against the same database.
- New accepted and rejected runner requests must extract required GitHub context in memory without persisting the raw webhook body. Keep `github_payload_json`, existing values, and historical metadata/installation-ID backfill logic for compatibility. Do not clear historical payloads or remove the column during startup; cleanup requires a separately authorized maintenance plan.
- State schema is defined mostly by GORM tags in `internal/state/records.go`; startup migration runs a narrow legacy compatibility pass and then `AutoMigrate` in `internal/state/db.go`. Existing SQLite `runner_requests` and `runner_profiles` tables are the exceptions: migrate their missing model columns and indexes additively because generic table recreation can erase ALTER-added runner-request values or legacy runner-profile rows and custom indexes. GORM foreign-key creation is disabled intentionally, so preserve the foreign-keyless schema convention unless a separately tested migration changes it. Legacy account preference/secret tables without scope columns are intentionally reset; operator docs must warn about Sandbox reconfiguration and GitHub reauthentication before installation sync.
- Global Runner Specs remain admin API/UI data. Ordinary users browse the read-only platform catalog at `/runner-specs`, while `/account/runner-specs` and `/organizations/{login}/runner-specs` contain only custom Specs owned by that scope; all three surfaces use `/user/runner-specs`. The platform page has no account/Organization selector and no per-scope enabled or concurrency controls. Internal Runner Groups and Repository Policies were removed completely in Release C: their management APIs return `404`, old Admin browser routes redirect to Runner Specs, and no current feature or recovery path may depend on legacy database artifacts.
- Ordinary-user Runner Spec responses may expose `template_id` and `runner_group` only for the selected scope's own `scoped_custom` entries. Managed entries expose their stable public template name and global read-only enabled/concurrency policy; read-only `platform_custom` entries must omit their private template IDs. Organization custom forms may edit `runner_group`; account forms must omit it. Keep async custom-list, template, and mutation follow-up responses bound to the scope that started them so an older account/Organization response cannot overwrite or submit against the current scope.
- Runner Spec/Sandbox mutations must commit their data change and audit event in the same database transaction. Rejected mutations leave no audit event, and audit persistence failures roll back the mutation. Managed catalog reconciliation follows the same atomic rule.
- Runner Spec names are trimmed, non-empty single-path-segment identifiers: new writes must reject names containing `/` and names equal to `.` or `..`. Apply the same validation to direct profile upserts and managed catalog reconciliation. Do not make startup, migration, list, state lookup, or matching reject historical path-unsafe rows, and never rename or delete those rows without a separately authorized data-repair plan.
- Runner Spec matching must preserve
  `required_labels ⊆ job_labels ⊆ labels`. Managed Ubuntu defaults require
  both `qiniu` and the exact OS label; never broaden them to accept partial
  label sets or unsupported extra labels.
- A claimed queued request must reload the persisted profile source and scope, apply the latest global or scoped-custom enabled state, and revalidate requested labels before registration or Sandbox creation. A disabled or changed spec fails at profile validation; never launch from admission-time state alone.
- runnerd owns the managed catalog's labels, required labels, stable public
  template name and priority. Operators own
  `enabled`, `max_concurrency`, and `min_idle`. The physical
  `runner_profiles.default_available` column is an inert legacy-schema
  compatibility detail and must not appear in APIs or influence matching.
  Custom specs remain operator-owned and retain explicit `template_id` and
  edit/delete behavior.
  Creating a custom spec or changing its trimmed template ID must validate using
  the configured admin Sandbox endpoint/key only, even when runtime fallback is
  disabled or audience-restricted. Never use user/organization credentials for
  admin validation. Missing config or failed validation rejects without profile
  or audit changes. Unchanged-template edits skip remote
  validation. Validate local fields before provider calls and keep provider I/O
  outside the audited transaction. Use conditional profile persistence to reject
  concurrent changes/deletes with 409 instead of restoring stale fields. Do not
  automatically repair historical specs.
- The unpublished `runner_profile_scope_controls` experiment is no longer part
  of the model, API, matching, capacity, or fresh schema. If an older feature
  database already contains that table, leave it intact but inert; do not read,
  recreate, or destructively drop it during startup.
- Resolve a managed spec's stable public template name against the
  account/organization scoped Sandbox endpoint immediately before runner
  registration. Never persist one region's default-template ID in a managed
  spec.
- The recommended production GitHub auth path is GitHub App auth for runner operations plus GitHub App OAuth sign-in for ordinary users and administrators. Local account roles authorize management APIs. Token and basic auth still exist as compatibility modes, but their long-term product status is undecided.

## Common Commands

```bash
task deps
task ui-deps
task ui-i18n-check
task ui-production-smoke
task dev
task smee
task lint
task test
task build
task docker-check
task release-check
task template-check-all
```

Use `task dev` for local development. It defaults to `RUNNERD_CONFIG=runnerd.local.yaml`, starts Vite on the first available localhost port at or after `5173`, and starts smee forwarding when `.smee-url` exists.

Use `task smee` for standalone GitHub webhook forwarding. It reads `.smee-url` and defaults to `SMEE_TARGET=http://127.0.0.1:25500/webhooks/github`.

Use `task build` when verifying production embedded UI behavior because it rebuilds `internal/server/ui/` before compiling `bin/runnerd`.

Public runner templates are built with `qiniu/qshell` 2.19.10 or newer.
`task template-build-ubuntu-*` performs the real remote template build and
requires `QINIU_SANDBOX_API_URL` plus `QINIU_API_KEY`. A local Docker build is
diagnostic only and does not prove that a Sandbox template exists or is
usable. Release evidence requires qshell `Status: ready` followed by
`task template-smoke` in both supported regions.

Use `cd ui && bun run test` for focused UI tests. `task test` rebuilds the UI, runs the Bun UI tests, and then runs Go tests with race detection and coverage.

Use `task ui-i18n-check` after changing UI copy or translation resources. It checks the English/Chinese resource contract, interpolation parity, typed i18next keys, and a narrow set of untranslated user-visible literals.

Use `task ui-production-smoke` after changing UI dependencies, Vite/Rollup configuration, manual chunking, production asset loading, public guides, or the Jobs viewport/scroll layout. It builds the production bundle, starts Vite preview on `RUNNERD_UI_SMOKE_PORT` (default `4173`), and runs headless Chromium coverage for the public landing page, responsive public hosted and custom-template guides, plus a local fixture-backed `/jobs` independent-scroll regression. It fails on browser errors, console errors, failed script/style requests, an empty root, missing expected headings or guide links, horizontal guide overflow, document-level desktop Jobs scrolling, coupled Jobs/Web Console scrolling, or clipped narrow-screen Jobs content. Because the local preview does not start `runnerd`, Playwright supplies the signed-out landing-page auth response and scoped authenticated Jobs API fixtures. Set `RUNNERD_UI_SMOKE_BASE_URL` to run the public browser canary against an already deployed origin; the local fixture-backed Jobs regression is skipped and the deployed canary must use the real auth endpoint.

When changing state records, GORM tags, indexes, migration helpers, or audited mutation semantics, run `go test ./internal/state -count=1` first. Old sqlite schema upgrade tests are intentional compatibility coverage; do not remove them just because fresh database creation passes. When a production export is available, run `RUNNERD_SQLITE_SNAPSHOT=/path/to/runnerd-export.db go test ./internal/state -run TestMigrateSQLiteRunnerRequestSnapshot -count=1 -v`. For cross-dialect schema, migration, or audited mutation changes, also run `Test(ApplyMutationWithAudit|FreshSchema|ScopedRunnerCatalogFreshSchema)SQLBackends` against dedicated PostgreSQL/MySQL databases whose names end in `_test`.

## Editing Rules

- Do not commit real secrets, local sqlite databases, or local config files.
- Do not commit `.smee-url`; it is per-developer local webhook state.
- Do not hand-edit generated files in `internal/server/ui/`; edit `ui/` and rebuild.
- Keep `README.md` and `README.zh.md`, `docs/testing.md` and `docs/zh/testing.md`, and `TODO.md` aligned when changing config, build, development, public APIs, authentication/authorization, state semantics, or deployment workflows.
- Keep `docs/README.md` and `docs/zh/README.md`, plus `docs/deployment-smoke.md` and `docs/zh/deployment-smoke.md`, aligned when adding or removing docs or deployment verification steps.
- Keep `.agents/rules/` and `.agents/skills/` aligned when a change creates durable agent rules or repeatable project workflows.
- Keep active future work in `TODO.md` and explicitly linked implementation records. When a plan completes or is retired, migrate durable rationale and compatibility boundaries into formal documentation, then remove obsolete execution checklists and their references.
- When changing ordinary-user UI, keep account/organization Preferences and Sandbox catalog scope separate from admin-only management APIs instead of assuming everything under `ui/` is admin-only.
