# Agent Guide

Use this guide for future Codex or agent work in this repository.

## Project Facts

- `runnerd` reads `./runnerd.yaml` by default, or another path passed with `--config`.
- Local development should use `runnerd.local.yaml` for secrets and sqlite state.
- Sensitive scalar config fields accept plaintext or `RUNNERD_ENC(v1:...)` generated by `runnerd --obfuscate-config-value`. The format only hides plaintext from casual inspection because its decoding key is embedded in runnerd. Keep sensitive values typed as `config.Secret`, call `Value()` only at their use sites, and preserve masked text, slog, JSON, and YAML output.
- UI source lives in `ui/`.
- Production UI assets are generated into `internal/server/ui/` by `task ui-build` and embedded by `internal/server/ui_assets_production.go`.
- Development UI assets are proxied to Vite by `internal/server/ui_assets_development.go`.
- `/` is always the public Qiniu CI Runner landing page. `/docs` and the exact guide routes declared in `ui/src/site-doc-routes.ts` are public; their paired English/Chinese Markdown sources live under `ui/src/content/site-docs/`. `/jobs` is the protected ordinary-user Jobs homepage. `/repositories` is the canonical GitHub repository access and effective Sandbox service readiness page; `/account/repositories` and `/organizations/{login}/repositories` are compatible scoped links to the same surface. `/runner-specs` is the protected, scope-free, read-only platform Runner Spec catalog. Account settings under `/account/runner-specs` and matching Organization routes manage only that scope's custom Specs; other protected settings include preferences, Sandbox templates, and Sandbox instances. Signed-out deep links must preserve their same-origin destination through OAuth `return_to`; unknown routes render 404.
- Deployment links share Jobs GitHub source-context prefixes, put the deployment ID in `/deployments/{id}`, and use `revision` to select saved history. `/deployments/{id}` without source context canonicalizes from local records; retired deployment source paths and `?deployment={id}` links are unsupported. Filter history against saved revisions before pagination, authorize reads through Jobs' exact repository cache and keep content provider-free, and never authorize by URL context.
- PR deployment titles are saved display snapshots. Legacy missing titles load through the separately authorized `/user/deployments/{id}/pull-request` metadata endpoint; keep detail/log reads local, reuse Jobs PR metadata caching, fill only empty titles for the exact ref, and preserve existing title snapshots and lifecycle timestamps. Branch/PR/Tag headings link to GitHub source pages.
- PR deployments execute the verified base-repository pull ref at a pinned head SHA, never a synthetic merge or fork-supplied URL. Retain fork source identity per revision, validate requested commit membership, and keep Sandbox authorization/credentials in the base repository scope. Old empty source snapshots remain valid.
- Deployment Web terminals require the opening account's current repository authorization and per-user shell ownership, bind the current running revision, attempt and Sandbox ID, and use the saved Sandbox credential/endpoint with remaining deployment lifetime. Historical revision pages cannot open the current Sandbox. Leaving the terminal or losing lifecycle/access closes the PTY; history content remains local. Transient SSE failures may resume the same PTY within twenty seconds using byte-offset `Last-Event-ID` replay from the bounded session tail. Reauthorize every reconnect, preserve the first subscription baseline even when reconnecting without a cursor, confirm recovery only from output or a heartbeat event, fail explicitly on replay gaps, and keep old idle timers from shortening the latest disconnect grace period.
- GitHub UI routes use repository collections `/github/{owner}/{repo}/{jobs|deployments}`, source filters `?branch=example/vite` or `?tag=release/v1`, and stable PR paths `/github/{owner}/{repo}/pull_requests/{number}/{jobs|deployments}`. Jobs without source context use `/runs/{number}/jobs`; Tags are deployment-only until Jobs retain reliable Tag evidence. Encode query values before restoring only `%2F` to `/`; never decode the whole query. Preserve older Jobs source-first and named-source paths, OAuth return, and fixed `commit`/resource/revision selections. Jobs filters apply within the existing authorized history window. Deployment history remains locally filtered before pagination. Job creation links pin the selected Job SHA; URL context never grants access and unavailable commits must not silently fall back to latest.
- Ordinary-user Job details default to Runner logs. Workflow step output is viewed through the GitHub Job link, with a Workflow Run fallback when repository/Run context is available. Do not duplicate or stream GitHub Actions logs in runnerd; the retired `/user/runner_requests/{id}/github-log` API returns `404`. Preserve Job status/result evidence and Runner lifecycle diagnostics.
- Ordinary-user Jobs authorization must use exact `(github_installation_id, repository_full_name)` pairs from the intersection of the stored GitHub user access token and each account-linked GitHub App installation. Never authorize Jobs from an installation link or installation-wide token alone; apply the same check to lists, details, groups, logs, and terminals, and fail closed when the user token is unavailable or rejected.
- Validate current user Installation metadata before accepting repository-list evidence: GitHub may return repositories for a suspended Installation. Reject missing or suspended installations through the shared GitHub repository-access boundary, including deployment admission, discovery and checkout; retain Jobs' bounded authorization cache.
- Sandbox service credentials and provider resource catalogs are ordinary-user account or organization data. Keep credential editing in the account or organization Preferences surface; `/repositories` only shows effective readiness and links there when a manageable scope is missing configuration. Repository-only access can make an organization installation and its authorized repositories visible, but Settings lists only the signed-in account and organizations where the user has an active GitHub membership with `role == admin` (a GitHub organization owner). The GitHub App therefore requires organization `Members: Read-only`; every existing installation owner must approve that permission when it is added, otherwise eligible organizations remain hidden from Settings. Apply the same owner-only manageable-scope check to installation-scoped preferences, Sandbox mutations, provider catalog reads, and custom Runner Specs; local runnerd admin status must not bypass GitHub organization ownership. Non-owners receive only `manageable: false` and effective readiness source from organization preferences, without API URL, secret status, Cache S3 fields, inheritance-account metadata, templates, instances, or scoped custom Specs. Keep credential-bound `/user/sandbox/templates` and `/user/sandbox/instances` separate from admin configuration APIs and from unauthenticated `GET /api/public/runner-templates`, which exposes only stable runnerd-owned public template names, logical Runner Spec names, and workflow labels.
- Organization fork sponsorship is owner-managed per exact upstream repository and applies only to public-name Specs. Verify stable fork/source/owner IDs plus exact approval, current upstream write permission, or active organization membership before provisioning. The Fork keeps Job and GitHub Runner ownership; never share the sponsor's Cache S3, custom Specs, physical template IDs, Runner Groups, credentials, Settings, or provider catalogs. Enforce a positive per-policy concurrency limit, snapshot credential-free sponsor provenance with the Sandbox config, clear both snapshots on fresh retry, and retain the saved snapshot for cleanup/recovery of an already-created Sandbox.
- Current admin browser routes include `/admin/`, `/admin/accounts`, `/admin/github_accounts`, `/admin/github_accounts/{installation_id}`, `/admin/runner_requests`, `/admin/runner_requests/{id}`, `/admin/sandbox_service`, and `/admin/diagnostics`; keep admin routes and role-gated APIs explicit when changing shared `ui/` code. Treat a Runner request as its own resource: the collection accepts exact Runner Name or internal Request ID lookup, resolves an exact Runner Name before an equal internal ID, and then navigates to the canonical internal-ID detail path. The canonical page aggregates persisted state, lifecycle timestamps and status-aware cleanup duration, credential-free version evidence, typed termination source and optional process exit code, findings, a retained terminal GitHub Job result or historical live fallback, and a cursor-paged mixed event timeline. After Sandbox readiness and before Runner launch, capture only the selected Sandbox region, resolved physical template ID, template version, and preinstalled Runner version; that probe must be allowlisted, limited to five seconds and 256 bytes per value, and nonfatal. Private-ID specs must resolve and validate GitHub's official Runner descriptors for the selected platform (Linux `.tar.gz`, or Windows `.zip` when the spec labels include `windows`) before registration preparation and replace a stale writable copy before Linux `config.sh` or the Windows JIT listener starts; public-name Specs skip that preflight, and both paths keep official self-update enabled after registration. Immediately before `RUNNERD_JOB_STARTED`, the fixed job-start hook may send one validated, 256-byte effective Runner version marker through a permission-restricted one-shot FIFO (Windows has no FIFO, so its hook atomically publishes a marker file that the outer script relays) to the outer startup process; hook stdout belongs to the GitHub Job log and is not an evidence channel. The Sandbox service accepts only the first valid pre-job marker forwarded by that outer process, freezes it in memory, ignores all later Workflow output for version evidence, and carries the frozen value in the matching Sandbox/PID exit callback even when the provider returns no command result. A runnerd restart after the marker may leave this best-effort field empty; recovery must not reconstruct it from Workflow-controlled output. Never persist or log the full environment, proxy values, tokens, keys, or cache credentials, and never write a region-specific physical template ID back to a managed spec. Fresh retry and mismatched-job requeue clear the snapshot, and historical empty fields remain valid. Cleanup Duration must use `stopping_at` and the terminal timestamp selected by the current request status; do not substitute `updated_at`, and treat missing, invalid, inverted, or Go-zero times as unavailable. `stopping_at` represents a real cleanup transition and must remain absent when a request reaches a terminal state without entering cleanup. Persist the first cleanup owner as `process_exit`, `workflow_job_webhook`, `manual_stop`, `recovery_cleanup`, or `failure_cleanup`; only persist an exit code from an observed process result, clear both fields before a fresh retry/requeue, and never infer an exit signal from `128+n` or a requested stop signal. Retain a Job result only for the request's original nonzero `workflow_job_id`, never for an assigned mismatched Job or a nonterminal observation; keep the observation time and Runner lifecycle status independent. Prefer the retained result in diagnostics and expose its source/freshness. Historical rows without a snapshot may use a live lookup; cache successful live lookups briefly and coalesce concurrent lookups for the same Job so polling cannot consume GitHub rate budget on every refresh. Diagnostic findings must use only a separately bounded `control_log` tail so raw output cannot create false signals or displace control evidence. Prefer typed termination evidence and stable `runner_exit`, `runner_hook`, and `runner_cleanup` stages before legacy control-message matching. The timeline loads newest events first, uses an exclusive `before_id` cursor for older pages, and renders every persisted control/stdout/stderr event directly as an individual chronological row without nested output cards or disclosures. Runner Hook, exit, and cleanup control events use stable `runner_hook`, `runner_exit`, `sandbox_cleanup`, `github_cleanup`, and `runner_cleanup` stages while legacy `control.log` reads remain compatible. Active request details refresh automatically through exclusive `after_id` pages until caught up, keep the older-history cursor independent, and merge new events without discarding or skipping loaded history; explicit refresh and stale-response protection remain required. Reserve Admin Diagnostics for current-process expvar, redacted runtime configuration, and pprof discovery. Keep diagnostic lookups admin-only, bounded, credential-free, useful when remote lookups fail, and keep legacy diagnostic deep links compatible. Ordinary-user `/user/runner_requests/{id}/events` must authorize the exact installation/repository pair and share the admin event pagination contract and timeline component; keep admin findings, request context, and mutations separate.
- `POST /runner_requests/{id}/network-diagnostics` is an admin-only, running-only action for a persisted Sandbox/PID attempt. Accept only `github_api`, `ubuntu_archive`, or `llvm_apt`; never accept a URL, host, command, header, or credential from the browser. Keep the full action within 10 seconds, connection within 3 seconds, transfer within 8 seconds, DNS evidence within 8 addresses, download and combined command stdout/stderr within 65,536 bytes each, retained error within 512 bytes, and each attempt to one concurrent call with a 30-second cooldown. Cancel the command when its combined output budget is exceeded. Discard raw command stderr and provider details; retain only server-owned probe error categories. Do not hold a Runner lifecycle lock during the provider call; reload and match status, Sandbox ID, and PID before retaining the credential-free result under the stable `network_diagnostic` control-event stage. Probe failure or timeout must not mutate request state, retry, termination, cleanup, or workflow timeout. Keep this evidence in the request detail timeline rather than adding a second export format unless a separately demonstrated handoff or archival need is authorized.
- `/admin/accounts` lists OAuth/bootstrap-created accounts and linked identities. Its only mutation changes another account's `admin`/`user` role atomically with an audit event; self-role changes and changes that could leave no administrator are rejected.
- `/admin/github_accounts` lists every current GitHub App installation reported through App authentication; `/admin/github_accounts/{installation_id}` loads that installation's current repository scope. Both surfaces and their APIs are admin-only and read-only, use the positive numeric installation ID for identity, and never substitute local OAuth accounts, cached installation owners, locally observed repositories, or ordinary-user OAuth intersection data.
- Runtime state can use sqlite, Postgres, or MySQL. Do not document multi-instance support until two runnerd processes have been verified against the same database.
- Prefer `cmd/runnerd-migrate` for SQLite-to-PostgreSQL migrations with a maintenance window; see `docs/sqlite-postgres-offline-migration.md`. Stop source and target writers, retain the private exclusive SQLite backup, require an empty PG schema and a successful verified transaction. Preserve keys and historical sequence watermarks. Active online fences require protocol finalization, not bypass. After PG accepts business writes, the old SQLite is not a lossless rollback target.
- Startup Job checks must defer recognized waiting states and monitor `in_progress` without provisioning, finish only on `completed`, and bound retries for unknown/query errors except HTTP 429 and GitHub secondary rate limits, which remain queued with capped backoff even after the failure budget is exhausted. Preserve delayed queue recovery and lease/capacity release. Only explicit admin retry with old control-log evidence and current queued/no-Runner/spec validation may recover historical waiting false completions; never bulk reopen terminal rows.
- Automated cleanup of a Runner that remained idle without accepting a Job records the additional `idle_cleanup` termination source; do not mislabel that successful cleanup as a failure.
- A Runner process that ends before accepting any Job (no assigned Job and no job-start marker) must not complete or fail its request outright, whether it exited 0 because GitHub terminated the listener, exited non-zero, or lost its Sandbox output stream while GitHub reports it idle. When Sandbox and GitHub Runner cleanup both succeeded, schedule a bounded `runner_exited_without_job` retry, clearing that attempt's termination source and exit code, so the start path rechecks the original Job before another Sandbox. Exhausted retries fail visibly.
- Bind every accepted process-exit watcher to the Sandbox ID and PID for its execution attempt. A matching result that arrives after another path owns cleanup may fill the missing exit code and append the stable `runner_exit` event, but it must not change termination ownership or repeat cleanup; a stale attempt must not mutate current state.
- New accepted and rejected runner requests must extract required GitHub context in memory without persisting the raw webhook body. Keep `github_payload_json`, existing values, and historical metadata/installation-ID backfill logic for compatibility. Do not clear historical payloads or remove the column during startup; cleanup requires a separately authorized maintenance plan.
- State schema is defined mostly by GORM tags in `internal/state/records.go`; startup migration runs a narrow legacy compatibility pass and then `AutoMigrate` in `internal/state/db.go`. Existing SQLite `runner_requests` and `runner_profiles` tables are the exceptions: migrate their missing model columns and indexes additively because generic table recreation can erase ALTER-added runner-request values or legacy runner-profile rows and custom indexes. GORM foreign-key creation is disabled intentionally, so preserve the foreign-keyless schema convention unless a separately tested migration changes it. Legacy account preference/secret tables without scope columns are intentionally reset; operator docs must warn about Sandbox reconfiguration and GitHub reauthentication before installation sync.
- Global Runner Specs remain admin API/UI data. Ordinary users browse the read-only platform catalog at `/runner-specs`, while `/account/runner-specs` and `/organizations/{login}/runner-specs` contain only custom Specs owned by that scope; all three surfaces use `/user/runner-specs`. The platform page has no account/Organization selector and no per-scope enabled or concurrency controls. Internal Runner Groups and Repository Policies were removed completely in Release C: their management APIs return `404`, old Admin browser routes redirect to Runner Specs, and no current feature or recovery path may depend on legacy database artifacts.
- Ordinary-user Runner Spec responses may expose `template_id` and `runner_group` only for the selected scope's own `scoped_custom` entries. Published public entries expose a stable template name when present (never a global physical ID) and global read-only enabled/concurrency policy; unpublished platform entries are omitted. Organization custom forms may edit `runner_group`; account forms must omit it. Keep async custom-list, template, and mutation follow-up responses bound to the scope that started them so an older account/Organization response cannot overwrite or submit against the current scope.
- Runner Spec/Sandbox mutations must commit their data change and audit event in the same database transaction. Rejected mutations leave no audit event, and audit persistence failures roll back the mutation. Profile policy migration follows the same atomic rule.
- Runner Spec names are trimmed, non-empty single-path-segment identifiers: new writes must reject names containing `/` and names equal to `.` or `..`. Apply the same validation to direct profile upserts and admin catalog mutations. Do not make startup, migration, list, state lookup, or matching reject historical path-unsafe rows, and never rename or delete those rows without a separately authorized data-repair plan.

  `required_labels ⊆ job_labels ⊆ labels`. Managed Ubuntu defaults require
  both `qiniu` and the exact OS label; never broaden them to accept partial
  label sets or unsupported extra labels.
- A claimed queued request must reload the persisted profile source and scope, apply the latest global or scoped-custom enabled state, and revalidate requested labels before registration or Sandbox creation. A disabled or changed spec fails at profile validation; never launch from admission-time state alone. Admission holds the shared side of the spec-mutation guard through the creating CAS; catalog mutations remain exclusive. Keep Store I/O outside the separate capacity reservation mutex. Count pending reservations and admissions made during an outstanding count read conservatively, release reservations after creating persistence returns on both success and failure, and retain global versus exact scoped-profile capacity boundaries. This coordination remains single-process.

Existing ID rows are not automatically published; IDs may also refer to public templates. Deleted rows must stay absent across restarts. `template_source` is a legacy reference/runtime discriminator, not provider visibility; `published` controls directory projection after admin provider validation. Admin has one Template field, with a read-only visibility check at `/runner_specs/templates/status`; public fixed-ID specs may display without changing reference or runtime. Public-name specs retain preinstalled Runner preparation, required Docker readiness and organization-policy sponsorship; fixed-ID specs retain official Runner preflight, optional Docker and no sponsorship. These behaviors are not independently configurable. Catalog display validates actual publicness with admin credentials for either names or IDs. New/changed bindings and re-enabled displayed specs additionally require a nonzero effective default BuildID. Name and ID runtime resolution share this rule; latest BuildStatus is only diagnostic and cannot invalidate an existing default. Preserve stored references on unchanged edits; unknown metadata must never be treated as private. Active execution-setting edits/deletes reject atomically; enabled/capacity/unpublish edits remain allowed.
  The physical `runner_profiles.default_available` column remains inert and must not appear in APIs or influence matching.

- The unpublished `runner_profile_scope_controls` experiment is no longer part

- Resolve a public-binding spec's stable template name against the
  account/organization scoped Sandbox endpoint immediately before runner

- The recommended production GitHub auth path is GitHub App auth for runner operations plus GitHub App OAuth sign-in for ordinary users and administrators. Local account roles authorize management APIs. Token and basic auth still exist as compatibility modes, but their long-term product status is undecided.

- Deploy startup recovery only signals the independent background scheduler; never execute queued plans under the HTTP startup recovery deadline. Deploy remains single-process; mixed-version writers are unsupported.

Use `task dev` for local development. It defaults to `RUNNERD_CONFIG=runnerd.local.yaml`, starts Vite on the first available localhost port at or after `5173`, and starts smee forwarding when `.smee-url` exists.

Use `task smee` for standalone GitHub webhook forwarding. It reads `.smee-url` and defaults to `SMEE_TARGET=http://127.0.0.1:25500/webhooks/github`.

Use `task build` when verifying production embedded UI behavior because it rebuilds `internal/server/ui/` before compiling `bin/runnerd`.

`Check` validates the application. `Template Check` (`.github/workflows/template-check.yaml`) runs template source tests, upstream compatibility and Dockerfile checks for related build/template/script changes or manual dispatch. Keep registry checks independent of source tests, use the shared `templates/` build context, and require both workflows on Runner upgrade PRs. Dockerfile `--check` does not replace real image builds or regional template acceptance.

regions.
`task template-build-all` invokes all eight build targets sequentially and stops
at the first failure; use it only when the whole regional catalog must be rebuilt.

Use `cd ui && bun run test` for focused UI tests. `task test` rebuilds the UI, runs the Bun UI tests, and then runs Go tests with race detection and coverage.

Use `task ui-i18n-check` after changing UI copy or translation resources. It checks the English/Chinese resource contract, interpolation parity, typed i18next keys, and a narrow set of untranslated user-visible literals.

Use `task ui-production-smoke` after changing UI dependencies, Vite/Rollup configuration, manual chunking, production asset loading, public guides, or the Jobs viewport/scroll layout. It builds the production bundle, starts Vite preview on `RUNNERD_UI_SMOKE_PORT` (default `4173`), and runs headless Chromium coverage for the public landing page, responsive public hosted and custom-template guides, plus local fixture-backed `/jobs` independent-scroll regression, `/runner-specs` publication filtering and narrow-screen Admin spec editing. It fails on browser errors, console errors, failed script/style requests, an empty root, missing expected headings or guide links, horizontal guide overflow, document-level desktop Jobs scrolling, coupled Jobs/Web Console scrolling, or clipped narrow-screen Jobs content. Because the local preview does not start `runnerd`, Playwright supplies the signed-out landing-page auth response and scoped authenticated Jobs API fixtures. Set `RUNNERD_UI_SMOKE_BASE_URL` to run the public browser canary against an already deployed origin; the local fixture-backed Jobs regression is skipped and the deployed canary must use the real auth endpoint.

When changing state records, GORM tags, indexes, migration helpers, or audited mutation semantics, run `go test ./internal/state -count=1` first. Old sqlite schema upgrade tests are intentional compatibility coverage; do not remove them just because fresh database creation passes. When a production export is available, run `RUNNERD_SQLITE_SNAPSHOT=/path/to/runnerd-export.db go test ./internal/state -run TestMigrateSQLiteRunnerRequestSnapshot -count=1 -v`. For cross-dialect schema, migration, or audited mutation changes, also run `Test(ApplyMutationWithAudit|FreshSchema|ScopedRunnerCatalogFreshSchema|RunnerProfilePolicy)SQLBackends` against dedicated PostgreSQL/MySQL databases whose names end in `_test`.

## Editing Rules

- Do not commit real secrets, local sqlite databases, or local config files.
- Do not commit `.smee-url`; it is per-developer local webhook state.
- Do not hand-edit generated files in `internal/server/ui/`; edit `ui/` and rebuild.
- UI changes must follow `.agents/rules/frontend-ui-consistency.md`. Reuse `ui/src/components/ui/` primitives and existing page patterns; form dropdowns must use the shared `Select`, never a new native `<select>` or page-specific imitation. Visual inconsistencies in the changed surface must be resolved before delivery; passing functional tests alone is insufficient.
- Keep `README.md` and `README.zh.md`, `docs/testing.md` and `docs/zh/testing.md`, and `TODO.md` aligned when changing config, build, development, public APIs, authentication/authorization, state semantics, or deployment workflows.
- Keep `docs/README.md` and `docs/zh/README.md`, plus `docs/deployment-smoke.md` and `docs/zh/deployment-smoke.md`, aligned when adding or removing docs or deployment verification steps.
- Keep `.agents/rules/` and `.agents/skills/` aligned when a change creates durable agent rules or repeatable project workflows.
- Keep active future work in `TODO.md` and explicitly linked implementation records. When a plan completes or is retired, migrate durable rationale and compatibility boundaries into formal documentation, then remove obsolete execution checklists and their references.
- When changing ordinary-user UI, keep account/organization Preferences and Sandbox catalog scope separate from admin-only management APIs instead of assuming everything under `ui/` is admin-only.

- Deployment list/detail workspaces share repository navigation. Keep `/user/deployment-repositories` independent of paged history, filter exact OAuth/App installation-repository pairs before aggregation/pagination, and expose only credential-free active summaries. Preserve terminal-only repositories, the selected terminal deployment, independent sidebar/content scrolling, source-filtered Jobs links and repository-prefilled creation.
- Deployment lists use a shared single-select segmented Toggle Group for `all`, `running`, `processing`, `stopped`, and `failed`, defaulting to All and retaining exactly one selection. URLs omit the status parameter for All; API requests always send the selected status. The API retains omitted/empty/`all` as all and rejects invalid, duplicate, or empty CSV members and repeated parameters. The All view orders running and processing deployments before retained terminal history. Filter unions in the local DB before pagination. `status_counts` must cover the full authorized source match before status filtering/pagination, group by current deployment state even for historical revision matches, and never filter the repository sidebar. Preserve source queries, URL/restored selection and stale-response isolation; details retain their separate output tabs.

- GitHub Runner group UX keeps repository registration as the default. Organization owners may read `/user/github-runner-groups?installation_id=<local-linked-id>` using that installation's GitHub credentials; account scopes and non-owners must not read group metadata. Group + label YAML must preserve label-based spec matching. Validate new/changed scoped groups and re-enablement before audited persistence, and check group/repository access before provisioning. Unchanged-group policy edits, disable/clear operations and historical values remain compatible; Admin global names have no single organization to validate at save time. Keep upstream errors redacted, bounded lookups and stale-scope response isolation.

- Deployments own numbered immutable revisions. Creation inserts #1; retry creates the next revision of the pinned plan in the audited transaction. Keep execution attempt fencing distinct, reject stale revision output, preserve old version state/logs, and budget retained events per revision. Revision reads share Jobs' exact installation/repository cache and keep content local. Store each revision's execution account separately from its immutable creator, and revalidate that actor before checkout. Preserve legacy rows/events through additive upgrade and import missing history as #1 without fabricating old status. Verify SQLite upgrades, real PostgreSQL/MySQL gates, cursor isolation, URL selection and stale UI responses.

- Deployment creation idempotency compares an immutable hash of normalized admission fields. Never reconstruct identity from mutable provider expiry or the current revision. Preserve the hash across retry and cleanup; historical empty hashes reject keyed replay. Cover concurrent admission, expiry precision changes, terminal replay, changed-input conflicts and revision changes.

- CI Runner owner/repository concurrency is configured through `worker.account_concurrency_limits` and `worker.repository_concurrency_limits`. Use the case-insensitive saved repository owner/name, independently of workflow actor, credentials, Installation ID and Spec scope. Count creating/running/stopping plus pending admission reservations; preserve default-unlimited scope behavior and single-process coordination. Capacity waits release leases without consuming failure retries and expose a stable `runner_capacity_*` reason. Configuration applies on restart; rename/transfer requires operator config updates.
