# 账户与仓库用量统计方案

## 目标与范围

管理员打开默认近 30 天的账户与仓库报表时，读取后台已发布的一批统计数据。Runner 入队、领取、创建、运行、清理和服务启动都可以独立于统计任务执行。首期覆盖 PostgreSQL 的 `/reports/account-usage`。SQLite、MySQL 和其他报表继续使用现有查询。各页面的覆盖率、时间窗口和样本定义见[用量报表口径](runner-reports.md)。

请求按原始入队日期归属。今天重试或完成的请求，可能会修正上周的启动数、运行时间或结果分布。账户按当前 Installation 映射识别。运行中的积压、执行尝试的日历期间用量、精确 P95 各有自己的数据来源。后续迁移这些指标时应保留原始样本、执行区间和采集起点。

## 数据如何产生

| 数据 | 粒度 | 用途 |
| --- | --- | --- |
| `report_account_facts` | 每个版本槽、每个请求一行 | 由现有 Go 口径计算单条请求贡献，包括精确维度、状态、时长、有效样本数和应有样本数。保留真实零时长和缺失时长的区别。 |
| `report_account_dirty_days` | 版本槽、UTC 入队日 | 和批次明细一起提交。中断后仍能找到待重算日期。 |
| `report_account_days` | 版本槽、UTC 日期和完整维度组合 | 对可相加的指标预先求和，保留账户、仓库和规格身份、Job 结果及最后入队时间。 |
| `report_account_dashboards` | 每个版本槽一份 | 保存默认 UTC、日粒度、近 30 天的汇总、趋势和完整排行。在高维度组合下也能直接读取。 |
| `report_account_publications` | 单行 | 记录已发布的版本槽、重建代次和统计截至时间。 |

独立 worker 通过两个专用 PostgreSQL 连接工作。同一数据库的写者通过会话级 advisory lock 互斥。同步在只读的可重复读事务里比对窄字段的 SHA-256 指纹。输入与 Go 指标计算共用同一份字段投影，包含 Installation owner 映射。数据库使用带类型和空值信息的二进制行表示，客户端只接收需要重算的记录。续租等无关写入不会触发重算。删除的源记录也参与核对。这样，迟到提交、重试、Owner 改名和映射删除都可以反映到下次发布。将来才生效的时间字段会在对应时点重新计算。worker 写入请求贡献时每批最多 256 行，每个脏日期单独更新汇总。初次创建和重建会再读一次源快照追平期间的变更，并在发布前核对源请求数、明细和日汇总的请求数、运行秒数与有效样本数。

当前方案每轮仍需在数据库内扫描报表源字段并核对指纹。节省的是重复计算、写入稳定历史，以及每次打开页面时对业务表的读取。两份统计明细和汇总需要额外磁盘，长时间的源快照也会影响 PostgreSQL 回收旧行。部署前应在代表性数据量下记录重建和增量耗时、磁盘和 WAL 增长、队列领取延迟。worker 错误和停止由独立进程处理。

## 发布与读取

后台只写未发布的版本槽。明细、日汇总和默认排行准备好后，单次数据库更新切换版本槽和截至时间。读取使用同一个可重复读事务。用户在报表中看到的观测时间来自源快照，分页沿用原有的限时快照，可跨服务实例恢复。

完整 UTC 日期读日汇总，截断日期和其他 IANA 时区读预先计算的明细。活跃账户、仓库、规格和本地日期在整个选中范围去重。Top 5 和“其他”取完整排序与分母。明细仍受本期与对比期合计 100,000 条的限制。跨过 UTC 午夜后，新日期范围会从同一批统计数据查询，直到下一批发布新的默认排行。默认排行超过快照预算时也走统计表查询。首次发布前，已切换的报表接口会返回 503；已有受支持的发布时，worker 停止后继续展示上次结果和截至时间。选定的整个窗口都晚于最后一次采集时返回 503。

## 运行、重建与回退

在已完成正常初始化的 PostgreSQL 上，使用与服务相同的状态库和 schema。worker 的 DSN 使用直连或支持会话绑定的连接池，使写者锁在多次提交之间持续有效。若服务端经事务池访问，可为 worker 单独配置指向同库的直连 DSN。worker 配置只需 `database.backend` 和 `database.dsn`，可以独立于 GitHub、OAuth 和 Sandbox 密钥分发。worker 是独立的 runnerd 命令，不监听 HTTP 或启动调度器。可先以单次模式建立并核对数据。

```sh
runnerd --config runnerd.yaml --account-reports=refresh
```

维护指标时，在共用的 Go 投影中修改资格、样本和时长规则。已存指标的含义改变时递增 `accountReportDefinition`，worker 会从源数据生成新代次。旧 worker 拒绝覆盖更新版本，服务只读取自己支持的定义。发布此类升级时先完成统计构建，再切换相应的服务版本。

在服务的 `database` 配置中设置 `published_account_reports: true`，随正常配置发布让账号报表读取统计表。用独立进程运行以下命令，每轮结束后等待五分钟再刷新。也可以用已有定时任务调用单次 `refresh`。

```sh
runnerd --config runnerd.yaml --account-reports=watch
```

修改指标口径、从逻辑备份恢复、批量修复数据或需要重新对账时，停止 watch，执行全量重建，再恢复 watch。重建使用新的代次，写入过程中旧报表仍可读。中止后重跑会复用已提交的批次。另一版本槽在下一轮使用同一代次重新计算。

```sh
runnerd --config runnerd.yaml --account-reports=rebuild
```

将 `published_account_reports` 恢复为 `false` 并按正常配置流程重启服务，即可回到业务表查询。统计表可以留存。执行期历史只能从已记录的业务事实还原，历史缺失值继续保留。

## 验证与上线条件

使用独立且名称以 `_test` 结尾的 PostgreSQL 测试库。专项用例创建自己的 schema。串行执行两个包，避免不同测试同时竞争统计写者锁。

```sh
export RUNNERD_CATALOG_BACKEND_TESTS=1
export RUNNERD_POSTGRES_TEST_DSN='postgres:///runnerd_test'
go test -p 1 ./internal/state ./internal/server -run 'TestPublishedAccount' -count=1 -v
RUNNERD_REPORT_SCALE_TEST=1 go test -p 1 ./internal/state ./internal/server -run TestPublishedAccount -count=1 -v
```

本地对账覆盖筛选、上一期、按本地日期分桶、迟到结果、重试、映射变更、删除、故障后的发布和重建。HTTP 用例检查未发布响应、默认入口和跨实例恢复。规模用例在重建和增量期间执行实际的数据库队列领取，并比较相同观测时点的原查询和已发布查询。

生产验收使用默认 30 天、无筛选、无快照的账户与仓库入口，要求在原有 10 秒期限内返回 HTTP 200。保留请求总数、运行样本和秒数、完整排行、Top 5 和“其他”的对账结果，复验第二页及下钻快照。另行比较等量队列负载下的领取延迟分布。效率与异常页继续单独验收。

## 2026-11-25 本地验收记录

PostgreSQL 17.11 的默认 UTC 近 30 天 HTTP 测试包含本期 255,027 条、对比期 255,000 条请求。每次请求使用新建的服务实例，共用数据库缓存。在管理员 HTTP handler 边界计时，包括统计读取、响应构建和报表快照持久化。

| 读取方式 | HTTP 状态 | 耗时 |
| --- | --- | ---: |
| 原查询 | 200 | 4.481 秒 |
| 后台已发布统计，首次打开 | 200 | 8.69 毫秒 |
| 后台已发布统计，独立重开 | 200 | 8.25 毫秒 |

两次发布路径的本期、对比期、趋势和排行均与原查询对齐。小窗口单独验证了跨服务恢复同一份分组及请求第二页，另外验证了报表写入故障期间的 Runner 生命周期、停写后的读取、原代次续跑、全量重建和统计定义升级。

另一组 51 万条合成请求用于队列实验。重建耗时 36.38 秒，稳定增量耗时 6.29 秒。每个窗口执行 10 次真实数据库领取。

| 领取窗口 | 中位数 | 最大值 |
| --- | ---: | ---: |
| 基线 | 1.011 毫秒 | 6.068 毫秒 |
| 重建期间 | 0.768 毫秒 | 2.369 毫秒 |
| 增量期间 | 0.705 毫秒 | 4.351 毫秒 |

这些结果覆盖本地合成负载。生产入口、代表性负载下的领取尾延迟、磁盘及 WAL 开销仍待上线验收。
