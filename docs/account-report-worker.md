# 账户与仓库用量统计方案

## 目标与范围

管理员打开默认近 30 天的账户与仓库报表时，读取后台已发布的一批统计数据。Runner 入队、领取、创建、运行、清理和服务启动都可以独立于统计任务执行。PostgreSQL 的 `/reports/account-usage` 使用已发布统计，`/reports/efficiency` 对默认 UTC 近 30 天、日粒度、无维度筛选的请求使用同一批次。SQLite、MySQL 和其他报表继续使用现有查询。各页面的覆盖率、时间窗口和样本定义见[用量报表口径](runner-reports.md)。

请求按原始入队日期归属。今天重试或完成的请求，可能会修正上周的启动数、运行时间或结果分布。账户按当前 Installation 映射识别。运行中的积压、执行尝试的日历期间用量、精确 P95 各有自己的数据来源。后续迁移这些指标时应保留原始样本、执行区间和采集起点。

## 数据如何产生

| 数据 | 粒度 | 用途 |
| --- | --- | --- |
| `report_account_facts` | 每个版本槽、每个请求一行 | 由现有 Go 口径计算单条请求贡献，包括精确维度、状态、时长、有效样本数和应有样本数。保留真实零时长和缺失时长的区别。 |
| `report_account_dirty_days` | 版本槽、UTC 入队日 | 和批次明细一起提交。中断后仍能找到待重算日期。 |
| `report_account_days` | 版本槽、UTC 日期和完整维度组合 | 对可相加的指标预先求和，保留账户、仓库和规格身份、Job 结果及最后入队时间。 |
| `report_account_dashboards` | 每个版本槽一份 | 保存默认 UTC、日粒度、近 30 天的汇总、趋势和完整排行。在高维度组合下也能直接读取。 |
| `report_account_publications` | 单行 | 记录已发布的版本槽、重建代次和统计截至时间。 |

runnerd 在启动后台任务时异步启动统计刷新。统计使用独立的 PostgreSQL 连接池，每轮最多三个连接，分别用于协调、读取源快照和提交批次。同库副本通过事务级 advisory lock 选出本轮写者，写入批次在提交前通过批次锁和协调事务的身份验证写入权。同步在只读的可重复读事务里比对窄字段的 SHA-256 指纹。输入与 Go 指标计算共用同一份字段投影，包含 Installation owner 映射。数据库使用带类型和空值信息的二进制行表示，客户端只接收需要重算的记录。续租等无关写入不会触发重算。删除的源记录也参与核对。这样，迟到提交、重试、Owner 改名和映射删除都可以反映到下次发布。将来才生效的时间字段会在对应时点重新计算。worker 写入请求贡献时每批最多 256 行，每个脏日期单独更新汇总。初次创建和重建会再读一次源快照追平期间的变更，并在发布前核对源请求数、明细和日汇总的请求数、运行秒数与有效样本数。

当前方案每轮仍需在数据库内扫描报表源字段并核对指纹。节省的是重复计算、写入稳定历史，以及每次打开页面时对业务表的读取。两份统计明细和汇总需要额外磁盘，长时间的源快照也会影响 PostgreSQL 回收旧行。部署前应在代表性数据量下记录重建和增量耗时、磁盘和 WAL 增长、队列领取延迟。统计失败写入服务日志，由后续后台轮次重试。

## 发布与读取

后台只写未发布的版本槽。明细、日汇总和默认排行准备好后，单次数据库更新切换版本槽和截至时间。读取使用同一个可重复读事务。用户在报表中看到的观测时间来自源快照，分页沿用原有的限时快照，可跨服务实例恢复。

完整 UTC 日期读日汇总，截断日期和其他 IANA 时区读预先计算的明细。活跃账户、仓库、规格和本地日期在整个选中范围去重。Top 5 和“其他”取完整排序与分母。明细仍受本期与对比期合计 100,000 条的限制。跨过 UTC 午夜后，新日期范围会从同一批统计数据查询，直到下一批发布新的默认排行。默认排行超过快照预算时也走统计表查询。首次发布前和滚动升级期间尚无兼容统计版本时，接口沿用原始数据查询及其时限。兼容版本发布后，各节点自动读取统计表。刷新失败时继续展示上次发布的结果和截至时间。选定窗口完全晚于最后一次采集时，接口使用原查询。

### 效率与异常的默认窗口

worker 从同一版本槽的请求明细中取启动、创建和清理时长，分别对有效样本计算最近秩 P95。零秒样本参与排序，无有效样本时返回空值。失败阶段、原因、终止来源及按 UTC 日期归档的准入拒绝趋势使用同一批明细。源字段指纹包含失败原因及终止来源，因此迟到的修正会触发重算。摘要与账户报表共用总计、对比期、趋势及统计截至时间，一次切换发布。小窗口内可下钻时，效率快照也保留当时的异常分类和时长样本。

账户统计沿用定义 2。新 worker 在独立连接上为统计明细添加可空列，保留旧版账户指纹，并单独记录效率指纹。新版重建中断后，旧节点可以接手未完成的代次，复用已写入的账户明细。效率定义随默认摘要写在同一份 JSON 中。旧节点发布账户摘要时会移除效率标记，新节点据此使用原查询，直到新版 worker 再次发布。

效率摘要使用 PostgreSQL 保存点。百分位或异常分组查询失败时，worker 记录错误，在本轮继续发布账户统计。效率页此时使用原查询及其 10 秒期限。已有兼容效率批次时，跨 UTC 零点的默认请求会按新窗口从同一批次的统计明细和日汇总计算，沿用该批次的截至时间。其他日期、粒度、时区和维度筛选继续使用原查询。当前积压独立读取实时状态。

## 运行、重建与回退

沿用现有的 `runnerd` 启动命令和数据库配置。每个 PostgreSQL 服务节点启动后立即检查一次，此后每分钟检查。持锁节点依据数据库时钟判断上次成功发布是否已满五分钟，或是否有中断的重建需要续跑。其余节点跳过本轮。运行中节点退出后，由其他副本的下一轮检查接手。服务启动、恢复和就绪检查均不等待统计完成。

日常刷新由服务负责。需要立即刷新，或从逻辑备份恢复、批量修正历史数据后需要全量重建时，可使用同一版本的维护命令。命令与所有后台节点共用写者锁，遇到正在运行的刷新会退出并报告冲突，稍后重试即可。

```sh
runnerd --config runnerd.yaml --account-reports=refresh
runnerd --config runnerd.yaml --account-reports=rebuild
```

重建写入未发布的版本槽，现有兼容版本在重建期间持续可读。中断后，后台刷新或再次执行重建都可以复用已提交的批次。修改账户指标的含义时递增 `accountReportDefinition`。效率指标单独使用 `efficiencyReportDefinition`，参与明细指纹计算和摘要读取校验。旧副本遇到更新的定义会跳过后台写入，继续按自身支持的口径读取。回退服务版本沿用正常的二进制回滚流程，保留统计表以备再次升级。执行期历史只能从已记录的业务事实还原。

## 验证与上线条件

使用独立且名称以 `_test` 结尾的 PostgreSQL 测试库。专项用例创建自己的 schema。串行执行两个包，避免不同测试同时竞争统计写者锁。

```sh
export RUNNERD_CATALOG_BACKEND_TESTS=1
export RUNNERD_POSTGRES_TEST_DSN='postgres:///runnerd_test'
go test -p 1 ./internal/state ./internal/server -run 'TestPublishedAccount' -count=1 -v
RUNNERD_REPORT_SCALE_TEST=1 go test -p 1 ./internal/state ./internal/server -run TestPublishedAccount -count=1 -v
```

混合版本回归使用 PR #209 合并提交 `0d48a0b` 编译的旧版 runnerd。将 `RUNNERD_TEST_ACCOUNT_V2_BINARY` 指向该可执行文件即可运行回滚用例，CI 会自动编译并传入。

本地对账覆盖筛选、上一期、按本地日期分桶、迟到结果、重试、映射变更、删除、故障后的发布和重建。HTTP 用例检查首次发布前的原查询、默认入口的自动切换和跨实例恢复。规模用例在重建和增量期间执行实际的数据库队列领取，并比较相同观测时点的原查询和已发布查询。

生产验收使用默认 30 天、无筛选、无快照的账户与仓库入口，要求在原有 10 秒期限内返回 HTTP 200。保留请求总数、运行样本和秒数、完整排行、Top 5 和“其他”的对账结果，复验第二页及下钻快照。另行比较等量队列负载下的领取延迟分布。效率与异常页继续单独验收。

## 2026-11-25 本地验收记录

PostgreSQL 17.11 的默认 UTC 近 30 天 HTTP 测试包含本期 255,027 条、对比期 255,000 条请求。每次请求使用新建的服务实例，共用数据库缓存。在管理员 HTTP handler 边界计时，包括统计读取、响应构建和报表快照持久化。

| 读取方式 | HTTP 状态 | 耗时 |
| --- | --- | ---: |
| 原查询 | 200 | 5.925 秒 |
| 后台已发布统计，首次打开 | 200 | 37.19 毫秒 |
| 后台已发布统计，独立重开 | 200 | 254.59 毫秒 |

两次发布路径的本期、对比期、趋势和排行均与原查询对齐。小窗口单独验证了跨服务恢复同一份分组及请求第二页，另外验证了报表写入故障期间的 Runner 生命周期、停写后的读取、原代次续跑、全量重建和统计定义升级。

另一组 51 万条合成请求用于队列实验。重建耗时 33.47 秒，稳定增量耗时 7.93 秒。每个窗口执行 10 次真实数据库领取。

| 领取窗口 | 中位数 | 最大值 |
| --- | ---: | ---: |
| 基线 | 0.712 毫秒 | 7.468 毫秒 |
| 重建期间 | 1.031 毫秒 | 2.993 毫秒 |
| 增量期间 | 0.755 毫秒 | 3.034 毫秒 |

另用两个以默认命令启动的 runnerd 进程连接同一个测试库。占住统计锁期间，两个服务均已开始处理 HTTP 请求。释放锁并停止其中一个进程后，另一节点在下一轮自动首次发布。一个新副本启动时保留了刚发布的版本，在原节点退出且统计到期后完成刷新。

这些结果覆盖本地合成负载。生产入口、代表性负载下的领取尾延迟、磁盘及 WAL 开销仍待上线验收。

## 2026-11-26 默认效率报表本地对账

PostgreSQL 17.11 的合成数据包含本期 255,030 条、对比期 255,000 条请求，覆盖成功、准入拒绝、启动前后失败、零秒和缺失时长。每次 HTTP 读取使用新的服务实例，计时包含读取和保存共享快照。默认效率入口原查询耗时 5.007 秒；后台发布后的两次独立读取分别耗时 7.55 毫秒、4.64 毫秒，均返回 200。三个阶段的有效样本数各为 204,000，启动、创建和清理的 P95 分别为 190、95 和 95 秒。原查询和两次发布读取的总计、对比期、趋势、排行分布及完整效率摘要相同。

混合版本回归中，新版重建在明细提交后、日汇总发布前中断，旧版 runnerd 接手了相同代次。旧版保留已提交明细的行版本，发布了中断前后新增的请求。重新升级后，效率摘要与原查询一致。另一组回归让百分位查询连续两轮报错，两个槽仍分别发布了新的账户总计，效率页恢复使用原查询。

跨 UTC 零点的规模用例包含本期 243,190 条、对比期 243,192 条请求，从上一批统计按新窗口读取耗时 5.88 秒。总计、对比期、趋势、排行和完整效率摘要均与同一观测时点的原查询相同。小窗口还核对了异常明细、首日边界，并在隐藏源表后验证跨日读取。

状态层另在同一发布时点与原查询对账，覆盖迟到修正和两个版本槽的重建。HTTP 回归验证了另一实例恢复旧快照的异常明细，超出明细上限时仍可读取分组第二页。上线后需单独复验生产默认入口的耗时与运行负载。
