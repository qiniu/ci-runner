# 平台 Runner 规格管理

数据库是平台 Runner 规格的权威来源。管理员在 `/admin/runner_specs` 维护所有规格，启动不再创建或协调代码内置目录。新安装的目录为空，需要恢复数据库备份或在后台创建规格后再提交 workflow。

## 模板引用与目录展示

| 字段 | 约束 |
| --- | --- |
| `template_source` | 兼容旧数据的引用／运行路径标记：`public` 使用稳定公共名称，`private` 使用物理 ID，不代表 Provider 的公开状态。 |
| `default_template_name` | 名称引用必填；每个请求按有效 Sandbox 区域独立解析。 |
| `template_id` | ID 引用必填；名称引用必须为空。 |
| `published` | 明确开启受保护目录中的展示；两种引用均须验证模板公开性；展示设置与运行可用性分开。 |

后台只保留一个“模板”字段，接受公共模板名称或物理 ID，不再提供“模板绑定”选择。管理员专用 `GET /runner_specs/templates/status?template=...` 使用后台 Sandbox 服务检查模板，区分 public、非 public、不可运行和无法确认状态；查询失败不等同于私有。验证为 public 后即可开启已有规格的目录展示；缺少可用默认构建单独提示，不阻止修改展示设置。新引用根据 Provider 元数据识别，精确 ID 优先；未改变的引用保留原有类型。新规格默认不进入目录。

后台在模板字段下方展示 Provider 返回的名称、ID、CPU／内存／磁盘配置、ENVD 版本及创建／更新时间；缺失值保持不可用。这些信息不进入普通用户的全局目录响应。

后台列表每个规格使用一张紧凑卡片，分别显示启用状态和目录展示状态、完整标签及必需标签、容量／优先级／组配置，并复用编辑框中的模板详情。规格与 Provider 信息独立加载。同一个已挂载列表内，相同模板引用合并请求，成功结果缓存 30 秒，最多同时查询 3 个；刷新会清除已完成的缓存。查询失败可重试且不修改已有设置，最后一个使用者离开后取消查询。模板详情不写入数据库。最新构建失败但仍有有效默认构建时，卡片和表单单独提示失败，不将模板判为不可用。公共名称运行时解析遵循同一规则；确实没有默认构建时仍在注册前失败。

名称和 ID 查询都需要先在 `/admin/sandbox_service` 保存端点和 API Key，账户或组织凭据不能替代这项后台配置。表单区分未配置服务、访问被拒绝、模板不存在和查询超时等原因。修正配置后可直接点击“重新获取”，无需关闭表单；查询失败会保留已有目录展示设置。

创建、更换模板、开启目录展示或重新启用已展示规格时，后端独立使用配置的 **Admin** Sandbox endpoint/key 校验，即使运行时 fallback 已关闭。名称必须唯一解析到 `public: true` 的模板。两种引用均以 Provider 目录中非零的有效默认 BuildID 判断可用性，不以最新 BuildStatus 或任意标签构建历史判断。创建、更换绑定及重新启用已展示规格时要求可用；已有规格只开启目录展示时仅要求公开。ID 使用 GetTemplate 的公开状态；只有详情标记 `public: true` 的 ID 才能展示。本地字段先校验，每次远程校验总计限时 5 秒，位于审计事务之外。拒绝或过期保存不修改规格和审计记录。模板不变的策略修改及关闭目录展示无需访问 Provider。公开状态在开启展示及更换模板时检查，列表读取不会轮询 Provider 或自动改写已存展示设置。

目录展示不改变执行行为：名称引用沿用预装 Runner、Docker 就绪要求及原有组织策略赞助；固定 ID 沿用注册前官方 Runner 检查／更新、尽力配置 Docker、不使用赞助，即使它指向公共模板。两类均保留官方自动更新，不新增准备、Docker 或赞助开关。

`/runner-specs` 展示启用且开启目录展示的规格，包括通过验证的公共模板固定 ID 规格。`/user/runner-specs` 保留名称引用的 `platform_public` 和 ID 引用的 `platform_custom` 来源，两者均可展示，同时返回 scope 自有 `scoped_custom` 条目；未开启展示的平台规格被省略。只有 scope 自定义条目返回物理 ID 和 GitHub Runner Group；全局 ID 条目省略模板详情，不编造稳定名称。匿名 `GET /api/public/runner-templates` 保留仅汇总稳定名称的契约，不包含只有 ID 的规格，只返回已启用、开启展示的名称引用及其 workflow labels。每进程缓存 60 秒并合并并发加载，Admin 成功保存／删除后使当前进程缓存失效；浏览器仍可缓存 60 秒。Provider 目录保持独立且受凭据约束。Large 规格可直接使用现有公共模板 ID 明确开启受保护目录展示，名称本身不会自动触发展示。

## 修改与升级兼容

名称保持为稳定资源标识。Admin 可编辑标签、必需标签、模板引用、GitHub Runner Group、优先级、启用状态、容量及目录展示设置。匹配继续遵守 `required_labels ⊆ job_labels ⊆ labels` 和 scope 精确覆盖。全局规格仍有 queued、creating、running 或 stopping 请求时，修改执行配置或删除会返回 `409 runner_spec_in_use`；容量、启用状态和发布状态仍可调整。CAS 拒绝过期保存，数据修改与审计事件原子提交。

增量迁移只转换尚无模板来源的旧行，保留标签、名称、管理员策略、时间戳和索引。绑定公共名称的旧托管行保留公开展示、预装 Runner、Docker 和赞助行为，清空已无用途的物理模板 ID。旧私有行保持不公开并使用官方更新准备；清空不参与运行的残留公共模板名称，避免后续修改其他字段时校验失败，同时保留物理模板 ID。缺少公共名称的历史托管行仍保持公共绑定且不公开，不将它自动改成可运行的私有规格。旧 `managed_by`、`catalog_revision` 列和值保留为不参与行为判断的兼容元数据。历史空／global 请求来源和保存的 Sandbox 快照仍有效。后续修改和删除在重启后保持，迁移不补建缺失规格，也不自动提升私有 large 规格。

升级前备份数据库。旧版本不理解新增目录字段，仍可能恢复代码内置规格，因此降级行为需要单独验证。未发布开发版本曾增加的 `runner_update_policy`、`require_docker` 和 `fork_sponsorship` 列不再创建或使用；已有这些列的数据库保留列和值，不做破坏性删除。另一个已退役的 `runner_profile_scope_controls` 表若已存在，也保持完整且不参与行为判断。修改公共别名后需验证 workflow 和区域运行 smoke，因为元数据校验不证明镜像内容。镜像构建、版本 pin 和发布仍由模板发布流程维护。

本次模板公开性调整不新增数据库列，也不迁移现有数据。已有 ID、名称、展示开关及运行路径在重启后均保持不变；管理员明确为已有公共 ID 规格开启展示即可。前一版本会拒绝编辑已展示的 ID 规格，若回滚后仍需编辑，应先关闭这些规格的目录展示。
