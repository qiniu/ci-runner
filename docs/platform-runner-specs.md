# Platform Runner Specs

The database is the authority for platform Runner Specs. Administrators maintain every spec at `/admin/runner_specs`; startup does not seed or reconcile a code-owned catalog. A fresh installation starts with an empty catalog. Restore a database backup or create specs in Admin before submitting workflows.

## Template references and catalog display

| Field | Contract |
| --- | --- |
| `template_source` | Legacy reference/runtime discriminator: `public` uses a stable public name; `private` uses a physical ID. These values do not describe provider visibility. |
| `default_template_name` | Required for a name reference; resolved independently through each request's effective Sandbox region. |
| `template_id` | Required for an ID reference; empty for name references. |
| `published` | Explicit opt-in to the protected directory; either reference type can display after provider publicness validation; display is independent of runtime readiness. |

Admin has one **Template** field accepting a public name or physical ID, with no binding selector. `GET /runner_specs/templates/status?template=...` is admin-only and checks the configured admin Sandbox service. It distinguishes public, non-public, non-runnable and unavailable metadata; unavailable metadata never implies privacy. The catalog checkbox can be enabled for a verified public template; a missing usable default build is reported separately and does not prevent changing an existing spec's display setting. New references are resolved using provider metadata, with exact IDs taking precedence; unchanged references retain their existing type. New specs start outside the directory.

The admin form shows credential-free provider template names, ID, CPU/memory/disk configuration, ENVD version and creation/update timestamps below the field; missing values remain unavailable. These details never enter ordinary-user global catalog responses.

The admin list uses one compact card per spec, showing enabled and directory-display states separately, full labels and required labels, capacity/priority/group settings and the same template details as the edit form. Specs load independently of provider metadata. Within a mounted list, identical template references share requests and successful results for 30 seconds, with at most three requests in flight; refresh invalidates completed results. Failed lookups offer retry without changing stored settings, and queries are canceled when their last consumer leaves. Template details are not persisted. If the latest build failed while an effective default remains available, the card/form reports that failure separately without declaring the template unusable. Public-name runtime resolution uses the same effective-default rule and still fails before registration when no default exists.

Both name and ID lookups require an endpoint and API key saved in `/admin/sandbox_service`; account or organization credentials do not substitute for this configuration. The form distinguishes missing configuration, access denial, missing templates and timeouts. After correcting configuration, use **Retry lookup** without closing the form; query failure leaves existing display settings intact.

Creating a spec, changing its template, enabling catalog display or re-enabling a displayed spec independently validates with the configured **admin** Sandbox endpoint/key, even when runtime fallback is disabled. Names must uniquely resolve to a public template. For both references, a nonzero effective default BuildID in the provider catalog proves readiness; latest BuildStatus and arbitrary tagged history do not. Creating/changing a binding or re-enabling a displayed spec requires readiness. Turning display on for an unchanged spec requires publicness only. For IDs, GetTemplate supplies visibility. IDs may display only when the detail metadata reports `public: true`. Local validation runs first; each provider validation has a five-second total deadline outside the audited transaction. Rejected/stale saves change neither profile nor audit. Unchanged-template policy edits and turning display off work without provider access. Provider visibility is checked when display is enabled or its template changes; reads do not poll the provider or automatically rewrite stored display settings.

Display does not change execution: name references retain preinstalled Runner preparation, required Docker readiness and existing organization-policy sponsorship. Fixed IDs retain official pre-registration Runner checks/update, best-effort Docker and no sponsorship, even for a public template. Both keep official self-update. No preparation, Docker or sponsorship switches are added.

`/runner-specs` shows enabled entries with catalog display on, including verified public fixed-ID templates. `/user/runner-specs` retains `platform_public` for name references and `platform_custom` for ID references; both can be displayed, alongside scope-owned `scoped_custom` entries. Unpublished platform entries are omitted. Only scoped custom entries expose physical IDs and GitHub Runner Groups. Global ID entries omit template details rather than inventing a stable name. The anonymous `GET /api/public/runner-templates` keeps its stable-name-only contract, so ID-only specs are absent there; it groups enabled, displayed name references and exposes names and workflow labels only. Its per-process cache lasts 60 seconds and coalesces fills; successful Admin saves/deletes invalidate that process cache. Browser caches may retain responses for 60 seconds. Provider catalogs remain separate credential-bound resources. Large specs can opt into the protected directory with their existing public template IDs; names alone never imply publication.

## Edits and compatibility

Names remain stable resource identifiers. Admin can edit labels, required labels, template reference, GitHub Runner Group, priority, enabled state, capacity and directory settings. Matching retains `required_labels ⊆ job_labels ⊆ labels` and scoped overrides. Execution-setting changes and deletion return `409 runner_spec_in_use` while queued/creating/running/stopping requests use that global spec; capacity, enabled state and publication may still change. CAS rejects stale writes. Mutations and audit events commit atomically.

The additive schema migration translates each row without a template source once, preserving labels, names, operator controls, timestamps and indexes. Old managed rows with public names retain publication, preinstalled preparation, Docker and sponsorship; their obsolete physical template ID is cleared. Old private rows remain unpublished with official preparation; any unused public template name is cleared so unrelated edits remain valid, while the physical template ID is preserved. Incomplete historical managed rows remain public-bound and unpublished; they are never silently converted into runnable private specs. Existing `managed_by` and `catalog_revision` columns/values are retained as inert compatibility metadata. Historical empty/global request sources and saved Sandbox snapshots remain valid. Later edits and deletes survive restart; the migration neither creates missing specs nor automatically promotes private large specs.

Back up the database before upgrading. Older binaries do not understand the new directory fields and may restore code-owned defaults, so downgrade behavior needs separate verification. The `runner_update_policy`, `require_docker` and `fork_sponsorship` columns from unpublished development builds are no longer created or used; existing columns and values remain intact. The separate retired `runner_profile_scope_controls` table also remains intact and inert if present. Changing a public alias requires workflow and regional runtime smoke, since validation proves provider metadata rather than image contents. Image building, pinning and publication stay in the template release workflow.

The template-visibility adjustment adds no columns or data migration. Existing IDs, names, display flags and runtime paths remain unchanged, including after restart. Operators explicitly enable display for existing public ID specs. The preceding release rejects edits to displayed ID specs; turn display off before rolling back to that release if those specs need to remain editable.
